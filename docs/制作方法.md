# 从线下卡牌到多人网页：一套可复用的制作方法

适用：由主持组织、玩家轮流抽牌、包含身份与现场任务的聚会卡牌。目标是制作配合现场游玩的网页版本。纯远程游戏需要另补语音、现场动作替代和远程争议处理；不能承诺任意卡牌只换图片就可上线。

本文从一个实际完成三轮规则澄清、实现和部署的项目提炼。方法可以迁移，具体规则必须重新确认。本项目未完成真实手机 Safari／微信、正式支付和公网容量验收，这些不能作为已验证能力宣传。

## 1. 先决定网页负责什么

网页适合负责：入场审批、座次、随机抽牌、剩余牌数、轮次、身份持有、计时、秘密输入、结果公布和断线恢复。

现场继续负责：口述、表演、实物传递、身体动作、自愿同意、安全判断和争议处理。软件无法证明动作完成，也不应伪装能识别玩家切换应用或实物位置。

先写一句产品边界：

> 让【谁】在【场景】用【设备】完成【流程】，由网页管理【状态】，由主持确认【现场行为】；首版不包含【范围外事项】。

开始前选一局真实玩法，主持按原规则走完，记录每次“谁决定、谁知道、何时结束”。不要先画完整首页。

## 2. 先找已有方案

以下是检索入口与选型判断，能力及维护情况应在新项目开始时复核（本次核查：2026-11-22）。

| 候选 | 适合 | 何时不选 |
| --- | --- | --- |
| [PlayingCards.io](https://playingcards.io/docs/overview) | 共享牌桌、自定义牌面、人工执行规则，先试玩最省开发 | 需要专属主持审批、隐私投影和严格自动判定时，先验证是否能覆盖 |
| [boardgame.io](https://github.com/boardgameio/boardgame.io) | 回合制规则、状态同步与多人框架 | 现场审批、相邻座次和控场接管仍需自己设计，不能假设框架自带 |
| 复用本项目 React + Express + Socket.IO + SQLite | 需要与本项目相近的现场主持流程 | 玩法不同也要重新建模，逐牌分支不会自动适配任意卡组 |

先用现成工具跑一次；只有关键流程无法覆盖时才开发专用网页。不先造可视化规则编辑器、脚本语言或万能卡牌引擎。

## 3. 把口头规则变成逐牌契约

第一步整理原始牌面、文字和授权来源，给每张牌稳定 ID。牌名修改不改变 ID。

每张卡至少填写：

| 字段 | 必须回答 |
| --- | --- |
| 原文与确认版本 | 哪句话来自原牌，哪句话是后续确认？ |
| 张数与入池条件 | 有限实体张数还是重复随机？0张是否禁用？ |
| 触发者／操作人 | 抽得者、目标还是主持操作？代操作是否改变归属？ |
| 目标 | 选几人？可否本人、离线者、未入座者？不足时怎么办？ |
| 执行动作 | 纯现场、选择、输入、持续身份、消耗道具还是软件小游戏？ |
| 可见范围 | 全场、本人、目标、原主持、当前控场分别能看到什么？ |
| 状态与寿命 | 何时生效、替换、使用、撤销、到期？ |
| 冲突 | 同名可否叠加？互斥身份、共享关系如何处理？ |
| 完成与跳过 | 谁确认完成？跳过是否退牌、回滚身份或产生罚次？ |
| 异常 | 暂停、断线、移出、重启、最后一张时怎么办？ |
| 动效 | 展示范围、时长、减少动态模式；是否影响结算？ |
| 确认状态 | 未定／已确认／已实现／已验证，四者分开 |

未填不等于同意默认值。矛盾逐条提问，记录用户最终决定；未定牌禁用。工作簿用于沟通，不能把自由文本直接当可执行规则导入。

例：持续身份卡需要明确“同名唯一还是叠加、旧持有人何时失效”；计时卡需要明确“暂停冻结还是继续、准确剩余时间谁可见”；两者都写成“抽到后执行”不足以开发。

## 4. 先定全局机制，再开发

按顺序交付三份文档，确认后才写新机制代码：

1. 机制设计：状态、权限、随机方式、结束条件、冲突、异常。
2. 开发计划：分阶段，列修改文件与每阶段验证条件。
3. 改造对比：原行为、新行为、兼容风险、数据迁移和回退。

只保留一份当前定稿；历史草稿标记被谁覆盖。最终规则不要散落在聊天、表格和旧文档中互相冲突。

最少先定这些全局问题：

- 入场是自由加入还是主持审批？座位按现场相邻关系还是任意编号？
- 原主持与当前控场是否不同？谁能收回？接管后是否暂停？
- 有限牌池还是带权重重复抽取？跳过是否消耗？何时算抽尽？
- 新玩家可否中途加入？当前任务名单是否固定？
- 谁能代抽、代选、代填？代填后是否还能参与猜测？
- 如何暂停、恢复、提前终止、保留座次再开局？

## 5. 把流程做成服务端状态机

可从最小流程开始：大厅 → 运行中的抽牌阶段 → 任务阶段 → 下一轮 → 结束；暂停作为受控状态保存恢复信息。

服务端负责随机、权限、计时和结算。浏览器发“请求抽牌”，不能提交“我抽中了什么”。每次变更检查房间、当前局、轮次、操作者、版本与目标；重复请求不能扣两张牌，过期请求不能改下一轮。

建议最少分开：房间、主持账号、参与者、座位、卡组配置、当前局、当前轮次、任务、持有记录。只有玩法需要才增加关系图与秘密答案。

客户端接收按身份生成的可见视图，不能先把答案广播给所有人再用 CSS 隐藏。日志、Socket 载荷、恢复快照都要检查，不能只看页面。

先写不可破坏的约束：

- 剩余张数不会为负；抽牌一次只消耗一张。
- 最后一张执行完成才结束，不能抽到就切结束页。
- 无权限者无法推进；暂停时无法偷偷修改任务。
- 同一请求只结算一次；重启不产生新牌或泄露未来牌序。
- 房间身份不能跨局写入；秘密只对允许的人可见。

有限实体牌池按剩余总张数等概率选择位置，不额外引入独立权重。任务不可执行时明确说明，由主持处理，不能静默换牌。

## 6. 用三个代表机制跑通纵向切片

先实现入场、座次、抽牌、现场确认、下一位和结束，再挑三类牌：

1. 普通现场任务：证明基本循环可用。
2. 持续身份：证明替换、持有展示和清理可用。
3. 秘密输入或计时任务：证明可见范围、暂停和恢复可用。

一台电脑开多个独立浏览器上下文验证，再扩展所有已确认卡。不要先把全部卡标“可用”再逐张补行为。

常见文件分工：shared 放类型和牌面定义；server 放规则、视图、存储与校验；src 放页面和交互；tests 放规则、恢复和多人浏览器验证。机制差异大时写清晰的显式分支，避免提前抽象万能规则语言。

## 7. UI先保证现场可操作

固定视觉约束：颜色、字体、字号、间距、按钮、弹窗和卡面比例。先做一张牌、一页大厅、一页牌桌作为样板。

牌桌优先展示当前轮到谁、当前卡、下一步；主持暂停与确认要易找到。长规则和长名单放可滚动面板，避免主要操作被推出手机首屏。颜色不能单独表达权限或结果。

卡面生成前定统一提示词和尺寸，保留来源及原图，网页压缩为 WebP。动效由同一服务端事件触发，本地关闭动画不等于结算。减少动态、声音开启与播放失败需要清楚反馈。

先用卡面加简单 CSS 光效。确有明确需求才加复杂专属动画；不要为了装饰新增视频生产线。

## 8. 验证要覆盖失败路径

| 层级 | 至少验证 |
| --- | --- |
| 规则 | 抽尽、跳过、冲突、目标不足、最后任务、同名替换 |
| 权限与隐私 | 玩家／控场／原主持／旁观视图、跨局请求、秘密载荷 |
| 时间与恢复 | 暂停冻结、重启恢复、断线接管后暂停、重复和过期请求 |
| 多人浏览器 | 从审批到结束；不同身份真实连接，不能仅点单人页面 |
| 布局 | 小屏、横屏、长昵称、满员、键盘、安全区、长内容 |
| 部署 | 生产入口、HTTPS、WebSocket、持久化、资源限制、回退 |
| 真机 | Safari／微信、扫码相机、声音、旋转和现场弱网 |

测试使用隔离数据目录和端口，禁止操作真实牌局。确定性规则测试、真实服务重启、浏览器检查各自证明不同内容；Chrome 模拟尺寸不能证明真机相机、声音或振动。

验收表分为：已实现、有证据验证、尚未验证。失败直接报错，不用默认卡、假响应或吞异常掩盖。

## 9. 部署与数据生命周期

代码发布目录与数据库分离；服务只回环监听，由 HTTPS 代理提供公网入口。小内存服务器在本机构建，设置服务资源限制。更新前确认活跃牌局，保留可执行回退路径。

分别定义上传头像、房间、会话、账号、支付订单的保留时间。支付是独立需求，不是卡牌网页化的必要步骤；不需要就保持关闭。开启前确认主体、隐私、退款、真实支付能力，不能照抄原运营者资料。

下线也算交付流程：备份专用代理配置 → 验证新配置 → 停止并禁用项目服务 → 公网返回明确下线状态 → 验证不再监听业务端口。其他站点、数据库、DNS和证书的处置分开，不因下线默认删除。

## 10. 发布前建立干净边界

从白名单导出公开副本，不在原工作区批量替换，不直接推旧 Git 历史。排除数据库、上传头像、会话、支付配置、环境文件、私钥、真实账号、运维记录、截图、私人 AGENTS 和带身份信息的工作簿。

公开示例里的运营者、联系邮箱和域名使用明确占位值；调整对应测试和协议版本。默认关闭支付，文档提醒实际运营前填写真实信息。

扫描文本只能发现一部分问题。逐项检查图片／音频／字体／卡牌原文的授权和元信息，确定代码许可与素材许可。没有依据时标记待确认，不擅自替素材所有者授予开源许可。

在公开副本运行检查与测试，再初始化新 Git 仓库。提交前检查暂存文件清单和完整 diff；先私有推送复查，再决定公开。许可证、素材授权和运行测试未完成时，称“发布候选”，不能称“已安全开源”。

## 可复制给AI的分阶段任务

> 我有一套线下卡牌，想制作现场配合手机使用的多人网页。先读取原始牌面和规则，输出逐牌契约与缺失问题，标明每条规则来源。先比较现成方案，不写代码。
>
> 规则确认后，输出机制设计、分阶段开发计划和改造对比。把网页职责、现场职责、权限矩阵、状态机、结束条件、秘密范围、断线与重启写清楚，等待确认。
>
> 确认后先实现普通任务、持续身份、秘密或计时任务三个纵向切片。服务端决定随机、权限和计时。使用隔离数据验证重复请求、跨局、暂停、断线和最后一张，再扩展其他已确认卡。未定牌禁用。
>
> 最后交付验收证据、未验证范围、部署回退说明及脱敏发布候选包。不要把模拟器、沙箱或代码检查写成真实设备、正式支付或容量验证。

完成标准：陌生主持能按文档开局，一组玩家能从入场玩到结束；断线恢复和权限隐私有证据；另一位开发者能换卡组、明确需要改的机制，并独立运行。
